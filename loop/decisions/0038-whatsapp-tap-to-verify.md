# ADR-0038: Sign in with WhatsApp by having the USER message the business number; a number-match reply confirms; the browser polls for the usual JWTs

**Status:** Accepted · **Date:** 2026-10-20 · **Deciders:** Vivek (pasted the design; "create new branch and do this and check"), agent · **Work item:** FEAT-027 · **Relates to:** ADR-0007 (OTP + JWT), ADR-0023 (admin door says nothing), ADR-0024/0034 (sessions), ADR-0027 (budgets), ADR-0037 (dev-only paths)

## Confidence
**Level:** Medium — the state machine, the signature check and the token issue are tested end to end against SIGNED webhook payloads in the exact Meta shapes; what is NOT yet exercised is a real Meta app on a public URL (business verification, a display name, a tunnel), and the one-in-three residual of button-based number matching is a product judgment (below).

## Research depth
**Quick check** (2026-10-20): developers.facebook.com — Cloud API interactive reply-buttons reference (request body; ≤ 3 buttons, title ≤ 20 chars, id ≤ 256; webhook `interactive.button_reply.{id,title}`; examples on Graph **v26.0**), Webhooks getting-started (`hub.mode=subscribe`, `hub.verify_token`, echo `hub.challenge`; `X-Hub-Signature-256: sha256=<hex>`), Cloud API webhook payload examples (`entry[].changes[].value.{metadata.phone_number_id, contacts[].profile.name, messages[].{from,id,timestamp,type,text.body}}`). The signature is HMAC-SHA256 of the raw body under the App Secret, hex — the documented shape; the raw bytes matter, so the app is created with `rawBody: true`.

## Context and problem
SMS OTP costs money per login and needs DLT; WhatsApp is where Indian societies live (BRIEF) and a message a USER starts is free. WhatsApp has already verified the sender's number, so a message arriving from a number is possession of that number — the same thing an OTP proves — provided the message can be tied to the browser that wants the session, and provided a victim cannot be tricked into sending it for an attacker.

## Options considered
1. **"Tap to verify" (chosen):** the browser gets a secret `requestId` and a semi-public code; the user sends "My Bulk Saving login code is BS-XXXXXX" from WhatsApp; the webhook ties the sender's number to the request and replies with a number-match prompt; the browser polls and receives the usual tokens. Pro: ₹0, three taps, nothing typed, no SMS provider. Con: Meta onboarding and a public webhook; one-in-three per lured message with buttons.
2. **WhatsApp OTP (we message them a code):** rejected — authentication-template conversations are billed per message; it is SMS economics with a different pipe.
3. **Meta's "Login with WhatsApp"/OAuth-style flows:** not available for this use; rejected.
4. **Tokens on the WhatsApp side (deep link back to the app with a one-time token):** rejected — the link would have to carry the session secret through WhatsApp's UI and a possibly different browser; polling with a browser-held secret keeps the secret where it started.

## Decision
1. **Two values, two trust levels.** `requestId` (32 random bytes, base64url) lives only in the browser that started the login and is the ONLY thing that can collect tokens. The `code` (`BS-` + 6 chars from an unambiguous alphabet, ~1.07×10⁹) rides in the WhatsApp message and is treated as semi-public: it can attach a number to a request, never issue a session.
2. **The state machine lives in Redis** (`wa:req:<requestId>`, 180 s; `wa:code:<code>` → requestId; Meta message ids deduplicated for 10 min), with CAS transitions in Lua: `pending → awaiting_confirm` (first text with the code; records the number and the WhatsApp profile name) `→ confirmed | denied` (a button tap from the SAME number) `→ consumed` (one status call collects the tokens; the next sees `expired`). Unknown and gone requests answer alike.
3. **Number matching with three buttons.** The browser shows a 2-digit number; the reply names the device ("Chrome · Android", from the start request's User-Agent) and asks which number is on the screen, with three buttons in random order. A wrong tap denies the request for good and tells the sender nothing happened. Residual, stated plainly: a resident lured into sending an attacker's pre-filled message has a **1-in-3** chance of tapping the attacker's number if they tap at all; each attempt costs the attacker a fresh lure (a denied code is dead), and a number may attach to at most **5 requests per hour**, so the hour's worst case is bounded, not eliminated. The wording carries the real defence ("only tap if that's you, right now").
4. **The same doors, the same rules.** Resident: the society is bound from the invite code at START and the resident is upserted at token time (`verifiedAt` stamped; the WhatsApp profile name is the default name of a NEW resident only). Admin: nothing on the WhatsApp side differs for an administrator's number — the prompt, the reply and the budgets are identical (ADR-0023); `findAdminByPhone` runs only at token time, and "not an administrator" is told only to the browser that started the request, after the number's owner tapped the right button — the OTP door's 403, one step later. Tokens come from `AuthService.issueTokens` — a lifetime per-device session like any other (ADR-0024/0034).
5. **Budgets** (ADR-0027's spirit): 10 starts per hour per client address; 5 attaches per hour per phone. The global throttler still applies to the polling.
6. **Modes, from the environment:** `cloud` when all five `WHATSAPP_*` variables are set (a partial set refuses to boot, like VAPID); `stub` when none are set and the dev echo is on (`OTP_DEV_LOG=true` + explicit `NODE_ENV=development|test`) — the sender logs and stashes its prompts, and a dev-only simulator (`/dev/whatsapp/*`, same gates as ADR-0037, loopback only) plays the WhatsApp side; otherwise `off`: `GET /auth/methods` says so and the start routes answer 404 `WHATSAPP_LOGIN_DISABLED`. Production can never be `stub` (the dev echo is refused there).
7. **The sender is an adapter** (`WHATSAPP_SENDER`): the Cloud API client POSTs `interactive`/`text` messages to `graph.facebook.com/<WHATSAPP_GRAPH_VERSION, default v26.0>/<phoneNumberId>/messages` with an 8 s timeout and redacted errors. It is the piece round updates over WhatsApp (ADR-0013's fast-follow) will reuse.
8. **Web:** the method choice is offered only when `/auth/methods` says WhatsApp is on; SMS OTP stays one tap away and unchanged. Phones open `wa.me/<number>?text=…`; laptops show a QR of the same link (`qrcode`, lazily imported) and the link itself for WhatsApp Web. Polling every 2 s stops on a terminal state or when the step unmounts.

## Consequences
Good: ₹0 per login, no SMS provider on the critical path, nothing to type; the token side is untouched; everything but Meta itself is provable on a laptop. Bad: a public HTTPS webhook and Meta onboarding (BRIEF R1) are prerequisites for the real thing; a dependency on Meta's availability and the number's quality rating (login messages are user-initiated and low-risk for it); numbers not on WhatsApp still need SMS; the one-in-three residual above.

## Revisit triggers
- Any report of a sign-in a resident did not start → replace the three buttons with a typed 2-digit reply (1-in-90) or a 10-row list (1-in-10), and alert on denied requests per phone.
- The first real Meta app: confirm the payload shapes against live traffic (the parser is tolerant; the integration suite uses the documented shapes) and set `WHATSAPP_GRAPH_VERSION` to a supported version.
- Round updates over WhatsApp: reuse `WHATSAPP_SENDER`, add template handling and the 24-hour-window rules there, not here.
